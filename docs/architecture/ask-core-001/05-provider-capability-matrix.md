# Provider capability matrix

Documentation reviewed 26 November 2026. “Documented” indicates an API capability. It does not establish AskHype access, availability for a specific model or compatible combinations. Gemini is integrated today. OpenAI and Anthropic require adapter fixtures, separate credential approval and live acceptance when authorized. No additional provider requests were made in this audit.

| Capability | Gemini Developer API | OpenAI Responses API | Anthropic Claude Messages API |
|---|---|---|---|
| Text, instructions and context | `generateContent`, system instruction and ordered user/model content parts. Currently sends flattened chat context. | Instructions and ordered input items. Send application history explicitly, with provider-hosted state disabled where supported. | Top-level system plus user/assistant messages and content blocks. |
| Streaming | `streamGenerateContent`; existing chat uses a completed response. | Typed response events including text deltas and completion. | SSE with content block events and stop reason. |
| Native web and citations | `google_search`, candidate metadata, chunks and grounding supports. Existing code extracts web chunks only. | Web Search tool, search action output, URL annotations with spans. Provider source lists are distinct from claims cited in text. | Versioned server-side Search tool, search result/citation blocks and tool limits. Handle errors embedded in successful HTTP responses. |
| Structured output and tools | JSON MIME/schema and declared tools; Search plus schema depends on actual model/API/project and remains inconclusive here. | Structured Outputs and function tools documented; verify specific tool/format/model combinations and schema subset. | Output schema and strict tool inputs documented. Claude documents incompatibility between citation blocks and strict JSON output. |
| Media inputs | Image/document multimodal parts and files on eligible models. Existing document extraction remains reusable. | Images and supported file inputs on eligible models. Verify PDF choice, attachment limits and retention. | Vision and PDF/document blocks on supported routes. Verify platform/version distinctions. |
| Usage and termination | Candidate finish reason and usage metadata; reported query list is not a billing ledger. | Response usage, status, incomplete details and tool actions. Reconcile separately billed tool calls. | Usage, stop reason and server tool usage where provided. Different response block/error shape. |
| Capability/config and availability | Documented Search for the deployed model identity. The controlled probe returned 402 even without Search, with production-project equivalence unverified. | Configured model and endpoint capabilities plus separately verified account entitlements. | Configured versioned tools, supported models and platform entitlements. Do not generalize from Bedrock to direct Messages. |

## Release verification per adapter

Use a versioned manifest keyed by provider, endpoint, SDK, model and project alias. Record supported combinations for text, tool calling, web evidence, streaming, image/file inputs and strict schema, plus request limits and privacy approval. A catalog declaration starts as unverified; enable a pair only after contract fixtures and a bounded authorized smoke. Record billing entitlement separately from capability and operational health. Currency, token/tool rates and budgets come from a reviewed configuration schedule with billing reconciliation. Provider usage fields may be missing and should stay unknown. No request-time model discovery is needed.

Isolate provider-specific research sessions, image calls and presentation planning behind separate services. Preserve native evidence and typed tool events through adapters. Avoid a universal schema that forces every provider to discard useful metadata or enables incompatible feature combinations.
