# Conversation and history audit

## Ownership and durable writes

- **Guest.** The browser stores a versioned conversation array and active UUID in localStorage. Storage failures are swallowed and the current state remains usable. Writes replace a snapshot. No cross-tab merge is implemented here. Image previews and generated SVG are omitted, and downloadable blobs are saved as unavailable metadata. A different device, cleared storage or an invalid saved object can look like lost history. [Storage functions](../../../src/utils/conversation-storage.ts#L29)
- **Account.** `initializeAuthenticatedHistory` lists Supabase conversations, conditionally imports guest items using stable IDs, then lists again. Migration markers are per user but the input guest store is device-local; shared-device import needs a deliberate ownership decision. Existing server history can suppress import and mark the migration complete. Read errors preserve existing in-memory state while showing a notice. A list failure or account transition can therefore leave stale UI state until hydration succeeds. [Shell initialization](../../../src/components/askhype/AskHypeShell.tsx#L67) · [Migration function](../../../src/services/conversation-repository.ts#L150)
- **Write sequence.** The shell creates the conversation, inserts user text, then updates the timestamp. Generation can overlap these writes. The assistant update appears immediately and is saved asynchronously only if the user-write chain succeeds. If any commit or subsequent metadata update fails, the transcript can be partial while the UI still has a reply. Upsert by message UUID prevents exact duplicate inserts using that UUID. Ordinary retries do not reuse an execution ID and a new generation can still produce a duplicate logical answer and another quota event. Refresh and lost-response recovery lack server-owned settlement. [Submit and persistence](../../../src/components/askhype/AskHypeShell.tsx#L188) · [Assistant persistence](../../../src/components/askhype/AskHypeShell.tsx#L299) · [PostgREST writes](../../../src/services/conversation-repository.ts#L91)
- **Ordering and pagination.** History performs one conversation query followed by one message query across returned IDs, ordered by client-provided timestamps. There is no explicit pagination or deterministic secondary ordering on ties. Large histories can hit the configured PostgREST row cap or request-size limit. A separate ordinary timestamp update may reorder a thread relative to a concurrent write. Different tabs keep separate React snapshots and there is no realtime/version reconciliation here. [List](../../../src/services/conversation-repository.ts#L65)
- **Identity boundary.** Postgres RLS requires `auth.uid()` and checks conversation ownership on message insert. UI uses a browser Supabase client, while backend privileged operations must enforce ownership explicitly. The chat request `conversation_id` is correlation metadata separate from the owned browser conversation UUID, and supplied history is untrusted input. Auth events include sign-in/out and token refresh. History effects have cancellation flags, but pending submissions and asynchronous writes are not generally scoped to an auth epoch. Sidebar and thread render the state without an ownership gate. Treat account switching, old tabs and post-delete in-flight replies as important repro cases. [History RLS](../../../supabase/migrations/202611220001_ask_p0_history_conversations.sql) · [Auth events](../../../src/auth/AuthContext.tsx#L105) · [Sidebar/thread binding](../../../src/components/askhype/AskHypeShell.tsx#L426)
- **Deletion and interruption.** UI removal precedes the database delete; failure is a notice and a later hydration may show the row again. A late completion can rebuild the in-memory conversation from its pending snapshot. Conversation deletion cascades messages and detaches linked research. Failed ordinary requests can leave a user row with no assistant reply. Chat has no token-stream resume path today. [Delete](../../../src/components/askhype/AskHypeShell.tsx#L361) · [Late completion](../../../src/components/askhype/AskHypeShell.tsx#L306) · [Research FK](../../../supabase/migrations/202611250001_research_conversation_lifecycle.sql)
- **Browser cache.** Workbox NetworkFirst matches broad HTTPS GET traffic and excludes `/api/research`. Authenticated PostgREST and usage GETs can match. RLS protects fresh server responses. Cache eligibility, matching, stale service-worker versions and surviving cache entries require a real browser isolation test, including offline reload and sign-out. A cross-account incident is unverified. Narrow to an explicit public asset allowlist and invalidate legacy cache entries during migration. [Service worker](../../../vite.config.ts#L48) · [Research list response](../../../backend/app/api/routes/research.py#L49)

## Deep Research and environment isolation

The start route uses a request UUID to look up an existing owned job before reserving again. The service creates a queued row and checks/links the conversation before provider creation. Worker and individual-job GET can reconcile the same job. The browser hook polls the list endpoint, which reads persisted state; it does not directly cause a provider poll. The worker selects up to 20 stale active rows and scans every 15 seconds. Conditional updates compare `updated_at` and active status. The completion trigger locks the owned parent, inserts a stable assistant message ID with conflict protection, and updates ordering inside the transaction. The browser merges completed jobs into the visible thread keyed by the same ID. In-memory projected research results are not in the ordinary outbound history until the underlying messages are refreshed. [Service](../../../backend/app/services/research_service.py#L43) · [Worker](../../../backend/app/services/research_worker.py#L11) · [Repository](../../../backend/app/repositories/research_repository.py#L69) · [Trigger](../../../supabase/migrations/202611250001_research_conversation_lifecycle.sql) · [Browser polling](../../../src/components/askhype/ResearchProgress.tsx#L7)

The brief reports shared Supabase. Both deployments can see the same profiles, quotas, jobs and conversations if configured against that project. Each FastAPI process starts a reconciler when quota enforcement and the research model are enabled. There is no lease or environment discriminator at the worker selection boundary. CAS and the completion trigger limit conflicts and duplicate assistant messages, but competing processes can make duplicate polls and use a credential from the wrong provider project. A crash between provider submission and durable provider ID update can orphan a remote job. The production worker count, key equivalence, database topology and incident attribution are unverified. [Lifespan](../../../backend/app/main.py#L22) · [Reservation and submit](../../../backend/app/services/research_service.py#L43)

**Containment proposal.** Inventory frontends, backend instances, service-role credentials, project IDs and worker eligibility without recording secrets. Keep one authorized reconciler for the shared job namespace until isolation is ready. Because the current startup couples worker activation to other settings, use an explicit worker gate in a separately approved release and avoid disabling quota as a workaround. Move staging to its own Supabase project, auth redirect allowlist, service credentials, provider project and synthetic accounts. Apply the same migrations there. Keep real production transcripts out of staging. Add worker lease/CAS ownership before enabling multiple reconcilers per namespace. Test linked deletion, duplicate poll, transaction rollback, retry and restore with disposable PostgreSQL. [Existing harness](../../../backend/scripts/validate_research_postgres.sh)

## Reproduction plan and target contract

Record stage/outcome and generated request/turn correlation IDs, auth transition category, SW version, hydration page size, and state version without message contents or tokens. Exercise browser refresh between each write, transient read/write errors, large histories, concurrent tabs, token refresh, logout/login, offline fallback, delete during generation, loss of HTTP response, and research completion while a tab is closed. Use separate synthetic accounts. The failure symptom in the brief is reported and unreproduced.

Move to application-owned account turns and provider-neutral history gradually. Keep guest local behavior, give the account an authoritative append/read service, and use keyset pagination, stable sequence and idempotent turn completion. Keep old rows readable through a compatibility projection. Canonical request, message, preferred language, evidence and attachment fields are specified in the [target architecture](06-target-architecture.md).
